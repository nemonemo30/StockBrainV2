## 1. システム構成

### 1.1 稼働環境

| 項目 | 内容 |
| --- | --- |
| 言語 | PHP 8.2.4 |
| フレームワーク | Laravel 12.69.2 |
| DB | SQLite（`database/database.sqlite`） |
| テンプレート | Blade（CSS はレイアウトに内包。ビルド不要） |
| 外部ライブラリ | phpoffice/phpspreadsheet ^5.10（Excel 読み取り） |
| 外部 API | 非公式 Yahoo チャート（保有株価）／ Google Gemini API（検索フォールバックと売買判断） |
| 定期実行 | Laravel スケジューラ + OS の cron |
| タイムゾーン | Asia/Tokyo |

SQLite を採用した理由は、単一利用者・単一口座の想定であり、
ファイル 1 つで完結してバックアップとリセットが容易なため。

| 区画 | 表示項目 |
| --- | --- |
| サマリー | 選択期間の合計実現損益、件数（利確／損切りの内訳）、勝率 |
| 期間別合計タブ | 今日／直近 7 日／今月／今年／全期間の合計。クリックでその期間に切り替え |

#### 集計期間の定義

| 値 | 表示名 | 範囲 |
| --- | --- | --- |
| `today` | 今日 | 当日 00:00:00 〜 23:59:59 |
| `days7` | 直近7日 | 6 日前 00:00:00 〜 現在 |
| `days30` | 直近30日 | 29 日前 00:00:00 〜 現在 |
| `this_month` | 今月 | 当月 1 日 00:00:00 〜 当月末 23:59:59 |
| `last_month` | 先月 | 前月 1 日 00:00:00 〜 前月末 23:59:59 |
| `this_year` | 今年 | 当年 1/1 00:00:00 〜 当年 12/31 23:59:59 |
| `all` | 全期間 | 制限なし |

既定値は `this_month`。未知の値が指定された場合も `this_month` に丸める。

## 3. 機能設計（バッチ）

### 3.1 セッション種別

現行の実行時刻は [運用メモ](../04_運用/運用メモ_共有用.md)。本番 cron はラッパーを直接叩く。

| セッション | 本番の時刻 | 処理 | 対応要件 |
| --- | --- | --- | --- |
| `morning` | 9:05 / 11:00 / 13:00 / 15:00 | ①株価取得 → ②機械的な損切り・利確・トレール・時間切れ → ③厳しい新規のみ | FR-04-01〜03 / FR-04-11 |
| `quotes` | 11:35 | 保有の株価だけ更新。売買しない。評価も書かない | FR-04-12 |
| `close` | 16:00 | 株価取得 → 評価損益を記録 | FR-04-07〜08 |
| `noon` | （本番では未使用） | `morning` と同じ処理。旧 12:00 | — |

### 3.2 処理フロー（morning / noon）

```
 1. job_runs に実行開始を記録（status = running）
 2. 保有銘柄の銘柄コードを収集
      └ 0 件なら株価取得をスキップ
 3. StockPriceFetcher で株価を取得
      ├ 成功 → holdings.current_price / price_as_of を更新
      └ 失敗 → current_price は更新しない（前回値を保持）
      └ 成功／失敗件数を job_runs に記録
 4. TradeAdvisor に判断を依頼（保有状況＋現金残高を提示）
      └ 応答（sells / buys / comment）を job_runs.ai_decision に保存
      └ --dry-run 指定時はここで終了
 5. TradeExecutor で売却を実行（利確・損切り）
      └ 1 件ごとに検証し、約定または見送りを実行ログに出力
 6. 買い候補の銘柄コードについて StockPriceFetcher で株価を取得
 7. TradeExecutor で購入を実行
      └ 銘柄マスタ照合／売買対象区分／株価取得成否／現金残高／単元株を検証
 8. job_runs に完了を記録（status = success）
```

例外が発生した場合は `status = failed` と例外メッセージを記録し、
ログに出力して異常終了コードを返す。

### 3.3 処理フロー（close）

```
 1. job_runs に実行開始を記録
 2. 保有銘柄の株価を取得し、holdings を更新
 3. 評価損益を算出し、portfolio_snapshots に当日分として保存
      └ 同一日の再実行時は更新（trading_date でユニーク）
 4. job_runs に完了を記録
```

### 3.4 株価取得方式

保有株価は **Yahoo チャートを先に取る**。日経平均の履歴と同じ非公式 API
（`query1.finance.yahoo.com/v8/finance/chart/{コード}.T`）の `regularMarketPrice`。
HTTP エラー・数値が無い・採否で弾いた銘柄だけ、従来の Gemini 検索に回す。
保有も新規買いも同じ `fetch`。顧問 JSON の数字は約定に使わない。

AI 経路は「JSON のみで出力せよ」と指示すると検索をサボるため、2 段に分ける。

| 順 | 内容 | 使うとき |
| --- | --- | --- |
| 1 | Yahoo チャート（`YahooQuoteClient`） | 保有と、買い候補の全銘柄 |
| 2 | Gemini 1 段目: 自然文で問い合わせる。出力形式は指定しない | Yahoo 失敗・不採用の銘柄だけ。検索あり |
| 3 | Gemini 2 段目: 回答文から JSON に整形 | 2 のあと。検索なし |

Gemini 1 段目に検索の証跡（`groundingMetadata`）がない場合は、
文言を強めて 1 回だけ再試行し、それでも証跡がなければその銘柄は取得失敗（FR-08-02）。

#### 採否の判定

Yahoo・AI どちらも `StockPriceFetcher::record` を通す。

| 判定順 | 条件 | 結果 |
| --- | --- | --- |
| 1 | 応答が得られない（Yahoo 失敗のあとに検索の裏付けなし／API エラー） | 不採用。残っていれば AI へ |
| 2 | 株価が数値でない、または 0 以下 | 不採用 |
| 3 | 対象日の年が確定できない、前年同日の記事、ニュース／25日線一覧（`QuoteDateGuard`） | 不採用。当日の前回値へフォールバックしない |
| 4 | 直近に **DB へ採用した株価** から許容乖離率（既定 50%）を超えて乖離 | 不採用 |
| 5 | 上記以外 | 採用 |

判定結果は理由・引用元とともに `price_quotes` に全件記録する（FR-08-04）。

- Yahoo は銘柄ごとに 1 リクエスト。AI に回すときは 5 件ずつ（チャンク分割）。
- Yahoo 成功時は数秒。AI 検索に回したときの実測は 5 銘柄で約 30 秒。

### 3.5 売買判断

出口は `DayTradeEngine` が先に機械的に売る（損切り・半分利確は 200 株以上のときだけ／100 株玉は +5% で全株・トレール・時間切れ）。  
Gemini（`TradeAdvisor`）は検索して、厳しい新規と根拠切れの `time_stop` だけを返す。損切り・利確は返させない。

買い候補の株価は保有と同じ `StockPriceFetcher::fetch`（Yahoo 先行）。取れなければ買わない。顧問の `price` は候補の足切りだけ。

`TradeAdvisor` は保有状況と現金残高を自然文で提示し、以下の JSON を要求する。

```json
{
  "sells": [{"code": "7203", "shares": 100, "action": "take_profit", "reason": "..."}],
  "buys":  [{"code": "6501", "shares": 100, "reason": "..."}],
  "comment": "今回の方針"
}
```

- `action` は `take_profit`（利確）／`stop_loss`（損切り）／`rebalance`（その他の売却）。
- 応答は正規化し、銘柄コードが空または株数が 0 以下の要素を除外する。
- 買い候補は上限件数（既定 5 件）で切り詰める。
- 取得に失敗した場合は空の判断（売買なし）として扱い、処理は継続する（NFR-04）。

### 3.6 約定処理の検証

`TradeExecutor` が「AI の判断」と「実際の約定」の間の関門となる。

#### 売却

| 検証順 | 条件 | 不成立時 |
| --- | --- | --- |
| 1 | 対象銘柄を保有している | 見送り |
| 2 | 現在株価が取得できている | 見送り |
| 3 | 売却株数 ≦ 保有株数（超過分は保有株数に丸める） | — |
| 4 | 単元株の倍数。一部売却の残りも 1 単元以上。割れない +5% は全株利確。既にある端株の全決済だけ単元未満を許す | 見送り |

成立時の処理:
- 実現損益 = `(現在株価 − 平均取得単価) × 売却株数`
- 現金残高に売却代金を加算
- 約定後株数が 0 なら保有を削除、1 以上なら株数のみ減算（**平均取得単価は変更しない**）
- `action` を実現損益の符号と突き合わせて補正（例: 損失なのに `take_profit` → `stop_loss`）

#### 購入

| 検証順 | 条件 | 不成立時 |
| --- | --- | --- |
| 1 | 銘柄マスタに存在する | 見送り |
| 2 | 売買対象区分（内国株式）である | 見送り |
| 3 | 株価取得が成功している | 見送り |
| 4 | 株数を単元株に切り下げ、さらに現金で買える単元数まで減らす | — |
| 5 | 結果の株数が 1 単元以上 | 見送り |

成立時の処理:
- 現金残高から約定代金を減算
- 新規購入は保有を作成、買い増しは加重平均で取得単価を更新
  `新取得単価 = (既存の取得金額 + 今回の約定代金) ÷ 合計株数`

売却・購入とも 1 件ごとに DB トランザクションで処理する（NFR-05）。

### 3.7 銘柄マスタ取り込み

| 項目 | 内容 |
| --- | --- |
| 入力 | JPX「東証上場銘柄一覧」`data_j.xlsx`（既定パス `storage/data_j.xlsx`） |
| 読み取り列 | 日付(A)／コード(B)／銘柄名(C)／市場・商品区分(D)／33業種区分(F)／17業種区分(H)／規模区分(J) |

| `job_runs` | セッションの実行ログ | 現行は 1 日 6 件（判断 4 + 株価更新 + 引け後） |
| `portfolio_snapshots` | 日次の評価損益 | 1 日 1 件 |
| `budget_entries` | 予算の登録履歴 | 登録ごと |
| `users` | 管理者ユーザー | 1 |

### 4.2 ER 関連

```
  portfolios ──1:N──▶ holdings
             ──1:N──▶ trades ──N:1──▶ job_runs
             ──1:N──▶ portfolio_snapshots ──N:1──▶ job_runs
             ──1:N──▶ budget_entries ──N:1──▶ users
                                 job_runs ──1:N──▶ price_quotes

  stocks ‥‥（銘柄コードで参照。FK は張らない）‥‥▶ holdings / trades / price_quotes
```

`stocks` との関連に外部キーを張らないのは、銘柄マスタを再取り込み・整理しても
過去の約定履歴が消えないようにするため。銘柄名は各履歴に複写して保持する。

### 4.4 計算式

| 項目 | 式 |
| --- | --- |
| 取得金額（簿価） | `平均取得単価 × 保有株数` |
| 評価額（時価） | `評価単価 × 保有株数`（評価単価 = 現在株価 ?? 平均取得単価） |
| 評価損益 | `評価額 − 取得金額` |
| 評価損益率 | `評価損益 ÷ 取得金額 × 100` |
| 総資産 | `現金残高 + 評価額合計` |
| 実現損益 | `(売却単価 − 平均取得単価) × 売却株数` |
| 累計実現損益 | `trades.realized_pl の合計` |
| 投入元本 | `portfolios.initial_cash` |
| トータルリターン | `(総資産 − 投入元本) ÷ 投入元本 × 100` |
| 売却時の取得単価（表示用） | `売却単価 − 実現損益 ÷ 売却株数` |
| 実現損益率 | `実現損益 ÷ (取得単価 × 売却株数) × 100` |
| 勝率 | `利確件数 ÷ (利確件数 + 損切り件数) × 100` |

売却時の取得単価を実現損益から逆算できるのは、一部売却でも平均取得単価を変更しない設計（3.6）のため。
このため `trades` に取得単価の列を持たない。

## 5. 設計上の主要な判断

| # | 判断 | 理由 |
| --- | --- | --- |
| 1 | 保有株価は Yahoo を先に取り、失敗分だけ AI 検索（自然文 → JSON 整形） | 検索だけでは銘柄ページの数字を取りこぼす。AI は JSON 指定時に検索を省略する（3.4） |
| 2 | 検索経路では裏付けがない株価を採用しない | 実在しない株価での約定を防ぐ（FR-08-02） |
| 3 | 直近株価から 50% 超乖離した値を採用しない | 幻覚および桁違いの値を排除する（FR-08-03） |
| 4 | 売買判断（AI）と約定検証（アプリ）を分離する | AI の誤指示でも DB の整合性を壊さない |
| 5 | 予算の入金で投入元本も増やす | 入金だけでトータルリターンがプラスに見える不具合を防ぐ（FR-09-05） |
| 6 | `action`（理由）と `shares_after`（数量）を別に持つ | 「利確／損切り／方針変更」と「全株／一部」は独立した軸であるため（4.3 trades） |
| 7 | `stocks` に外部キーを張らない | 銘柄マスタの再取り込みで履歴を失わない |
| 8 | 株価取得の入口を `StockPriceFetcher` に閉じる | Yahoo / AI / 将来の証券会社 API の差し替えをここに集める（NFR-08） |
| 9 | CSS をレイアウトに内包する | npm ビルドなしで動作させる |
| 10 | 一部売却で平均取得単価を変えない | 実現損益から取得単価を逆算可能にし、列の重複を避ける |

## 7. 運用設計

### 7.1 初期構築手順

```bash
composer install
cp .env.example .env

# .env に GEMINI_API_KEY / ADMIN_EMAIL / ADMIN_PASSWORD を設定

```

### 7.2 定期実行の登録

本番は Lolipop の cron がラッパーを直接叩く（[運用メモ](../04_運用/運用メモ_共有用.md)）。

| 時刻 | ファイル |
| --- | --- |
| 9:05 / 11:00 / 13:00 / 15:00 | `cron-morning.php` |
| 11:35 | `cron-quotes.php` |
| 16:00 | `cron-close.php` |

`routes/console.php` の 9:00 / 12:00 / 16:00（`schedule:run`）は現行運用ではない。ローカルでスケジューラを使うとき用に残している。
